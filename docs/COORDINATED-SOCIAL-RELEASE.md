# Coordinated website release

AliaSpaces publication now borrows the actual MyPersonas `production-release` lock through a dedicated upstream lease workflow. Repository-local concurrency names do not coordinate different repositories. No new cross-repository write credential is needed: both repositories are public and the consumer only reads the upstream receipt/run; the upstream only observes the consumer.

1. Review and merge the source fixes and AliaSpaces pin. Keep both main tips frozen.
2. Complete the normal migration/canary evidence gates and obtain the exact successful MyPersonas backend run. A reused canary must be identified as reused and justified by unchanged relevant code; a successful historic run alone does not attest the active backend.
3. Publish MyPersonas through its normal reviewed Pages workflow. Under the existing production lock it now downloads the active caption functions into temporary directories and compares all six returned source members against Git, requiring JWT verification.
4. Dispatch `social-release-lease.yml` on MyPersonas main with exact AliaSpaces main SHA, backend run ID and `COORDINATED-SOCIAL-RELEASE-VERIFIED`; approve the normal production environment. The job acquires the same lock as backend and MyPersonas Pages, reads the active backend source/JWT, then publishes `social-release-lease-RUN/lease.json`.
5. While its named holding step is running, start one fresh AliaSpaces Pages run with the normal evidence and `upstream_release_run_id=RUN`. Start the consumer job within ten minutes after lease issue. The upstream selects exactly one run and publishes a second consumer.json receipt binding its run ID/attempt; no other run can borrow that lease. Its twenty-minute job timeout and first-run-only requirement prevent delayed reruns from reusing the lease. The receipt binds both main revisions and the backend run. The live upstream run/holding step is checked before build and immediately before Pages publication.
6. The upstream holds its lock until that exact consumer completes, then rechecks the backend. Temporary control-plane read failures retain the lock. Its forty-minute watch and sixty-minute workflow timeout exceed ten-minute admission plus twenty-minute consumer runtime with additional safety margin. Do not manually cancel the lease or downstream run to bypass a deployment wait; inspect uncertain outcomes before starting another release.
7. Read back the deployed artifacts, private-path exclusions, identity/preview behavior and final backend source. Keep hosted, browser and device acceptance separate.

No schema migrations, provider sends, model inference, account changes or device installation are performed by the lease. The existing Supabase deployment credential is used only for read-only source/metadata verification. CLI2.115.0 is pinned to the already qualified deployment version; downloads use `--use-api` and isolated temporary output. No access token, downloaded source or user data appears in the public lease receipt, which contains code hashes and release identifiers only.

The lock covers repository-managed deployment workflows, not an administrator changing Supabase manually or force-canceling protection. Such interventions invalidate the release receipt and require renewed verification. Failed, expired or reused leases are not authority to weaken the release guards.
